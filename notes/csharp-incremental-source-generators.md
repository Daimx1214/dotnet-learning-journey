# C# Incremental Source Generators

Source generators run at compile time and produce C# code that becomes part of the compilation. The original `ISourceGenerator` API works, but it re-runs the whole generator on every keystroke in the IDE and every build, which slows down large solutions. Incremental generators, built on `IIncrementalGenerator`, fix that with caching.

## Why Incremental Generators Matter

An `ISourceGenerator` receives the full compilation on every invocation and must do all of its work again, even if only one file changed. An incremental generator builds a pipeline of small steps, and Roslyn caches the result of each step. When one input changes, only the steps downstream of that input re-run. On a big solution this is the difference between a generator that is invisible and one that makes every build noticeably slower.

## The Pipeline Model

An incremental generator works with values that carry change tracking:

- `IncrementalValueProvider<T>`: a single value produced by a step, for example the compilation.
- `IncrementalValuesProvider<T>`: a sequence of values, for example all syntax nodes with an attribute.
- `RegisterSourceOutput`: the final step that emits generated source files.
- `Select`, `Where`, `Combine`, `Collect`: transforms that connect the steps.

Each step only re-runs when its inputs change, and Roslyn compares outputs by value to decide whether downstream steps must run.

## Finding the Inputs

`SyntaxProvider` exposes the syntax tree. `ForAttributeWithMetadataName` is the efficient way to find attributed declarations without scanning every node yourself:

```csharp
var targets = context.SyntaxProvider
    .ForAttributeWithMetadataName(
        "MyApp.GenerateToStringAttribute",
        predicate: static (node, _) => node is TypeDeclarationSyntax,
        transform: static (ctx, _) => (INamedTypeSymbol)ctx.TargetSymbol);
```

The predicate runs on syntax only and must be cheap. The transform runs on the semantic model and produces the data the generator needs. Keep the transform output small and equatable: prefer records or plain data over raw symbols, because symbols are compared by reference and can defeat caching.

## A Small Example: Generate a Registry

Suppose an attribute marks handler classes, and the generator emits a registry that lists them all:

```csharp
[Generator]
public class RegistryGenerator : IIncrementalGenerator
{
    public void Initialize(IncrementalGeneratorInitializationContext context)
    {
        var handlers = context.SyntaxProvider
            .ForAttributeWithMetadataName(
                "MyApp.HandlerAttribute",
                predicate: static (node, _) => node is ClassDeclarationSyntax,
                transform: static (ctx, _) => ((INamedTypeSymbol)ctx.TargetSymbol)
                    .ToDisplayString(SymbolDisplayFormat.FullyQualifiedFormat))
            .Collect();

        context.RegisterSourceOutput(handlers, static (spc, names) =>
        {
            var code = new StringBuilder();
            code.AppendLine("// <auto-generated/>");
            code.AppendLine("namespace MyApp;");
            code.AppendLine("public static class HandlerRegistry");
            code.AppendLine("{");
            code.AppendLine("    public static readonly string[] Handlers =");
            code.AppendLine("    {");
            foreach (var name in names)
                code.AppendLine($"        \"{name}\",");
            code.AppendLine("    };");
            code.AppendLine("}");
            spc.AddSource("HandlerRegistry.g.cs", code.ToString());
        });
    }
}
```

Adding one new handler only re-runs the transform for that class and the final output step, not the whole pipeline.

## Rules That Keep Generators Fast

- Never do expensive work in the predicate; it runs on every syntax node.
- Emit data, not symbols, from transforms. A `record` with strings is compared by value and caches well.
- Use `ForAttributeWithMetadataName` instead of `CreateSyntaxProvider` with a broad predicate when an attribute is the trigger.
- Keep generated code deterministic: same inputs must produce the same output, or incremental builds thrash.
- Put the generator in its own project referenced with `OutputItemType="Analyzer"` and `ReferenceOutputAssembly="false"`.

## Debugging

Generators run inside the compiler, so `Console.WriteLine` goes nowhere. Use `Debugger.Launch()` guarded by a check, or emit diagnostics with `spc.ReportDiagnostic`. The generated files can be inspected by setting `<EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles>` in the consuming project.

## Key Takeaways

- Incremental generators cache each pipeline step, so only changed inputs re-run; `ISourceGenerator` re-runs everything.
- Build pipelines from `IncrementalValueProvider` steps and finish with `RegisterSourceOutput`.
- Use `ForAttributeWithMetadataName` to find attributed declarations efficiently.
- Transform syntax into small equatable data, not raw symbols, to keep caching effective.
- Deterministic output is required, or incremental builds lose their benefit.
