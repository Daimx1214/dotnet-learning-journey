# UUID vs Int Identity Keys

Every table needs a primary key, and the two common choices behave very differently. An `int` identity column is small, fast, and sequential. A UUID (GUID) is globally unique and safe to generate anywhere, but its randomness has a cost in SQL Server.

## Int Identity Keys

```sql
CREATE TABLE Orders (
    Id INT IDENTITY(1,1) PRIMARY KEY,
    CustomerName NVARCHAR(100) NOT NULL
);
```

An `int` identity key is 4 bytes, sequential, and generated by the database on insert. Sequential inserts append to the end of the clustered index, which keeps pages full and fragmentation near zero. The downside is that the key does not exist until after the insert, so the application cannot know the id of a new entity before saving it, and ids are predictable, which leaks rough record counts and creation order through URLs.

An `int` tops out at about 2.1 billion rows, which is plenty for most tables. `bigint` raises that to 9.2 quintillion at the cost of 8 bytes per key and per foreign key reference.

## Random GUIDs: Guid.NewGuid()

```csharp
public class Order
{
    public Guid Id { get; set; } = Guid.NewGuid();
    public string CustomerName { get; set; } = string.Empty;
}
```

`Guid.NewGuid()` produces a version 4 UUID: 122 random bits, generated in the application with no database round trip. The id is known before the insert, it is not guessable, and two services can create records independently without coordinating, which is why distributed systems and offline-first apps favour GUIDs.

The cost is in the clustered index. SQL Server's default primary key is clustered, so rows are stored in key order. Random GUIDs insert at random positions in the index, which splits pages, leaves them half empty, and fragments the index. Write-heavy tables with random GUID keys can fragment badly and waste disk and memory.

## Sequential GUIDs: NEWSEQUENTIALID()

SQL Server offers a middle ground: `NEWSEQUENTIALID()` generates GUIDs that increase over time on one machine, so inserts append instead of scattering:

```sql
CREATE TABLE Orders (
    Id UNIQUEIDENTIFIER DEFAULT NEWSEQUENTIALID() PRIMARY KEY,
    CustomerName NVARCHAR(100) NOT NULL
);
```

In EF Core, configure the default value in the model:

```csharp
modelBuilder.Entity<Order>()
    .Property(o => o.Id)
    .HasDefaultValueSql("NEWSEQUENTIALID()");
```

Sequential GUIDs keep the global uniqueness and pre-generation benefits while behaving like identity columns for the clustered index. The trade-off is that they are generated by the database, not the application, so the id is not known before the insert, and their ordering is only guaranteed per machine, so a multi-node setup can still interleave.

## Guid.CreateVersion7: The Modern Option

.NET 9 added `Guid.CreateVersion7()`, a time-ordered UUID that the application can generate itself:

```csharp
public class Order
{
    public Guid Id { get; set; } = Guid.CreateVersion7();
    public string CustomerName { get; set; } = string.Empty;
}
```

Version 7 GUIDs start with a Unix millisecond timestamp, so they sort in creation order and insert sequentially into a clustered index, while still being generated client-side with no round trip. For new .NET 9 applications that want GUID keys, this is the best default. Note that `CreateVersion7` was added in .NET 9, so older targets need a library or `NEWSEQUENTIALID()`.

## HiLo: The Other Alternative

HiLo gives the application sequential ids without a database round trip per row. The database holds a "high" value; the application reserves a block of ids (say 100) and hands out "low" values locally until the block is exhausted:

```csharp
modelBuilder.Entity<Order>()
    .Property(o => o.Id)
    .UseHiLo("OrderSequence");
```

HiLo keys are small integers, sequential, and known before insert, which is the best of both worlds for a single database. The cost is complexity: sequence gaps appear when an application restarts with unused ids, and the mechanism is tied to one database, so it fits single-database apps better than distributed ones.

## Choosing

| Situation | Best choice |
|-----------|-------------|
| Single database, simple app | `int` identity |
| Distributed services creating rows independently | GUID, preferably version 7 |
| GUID keys on SQL Server, .NET 8 or earlier | `NEWSEQUENTIALID()` |
| Single database, ids needed before insert | HiLo |
| Public-facing ids in URLs | GUID, since sequential ids leak order and count |

One more option: keep the `int` identity as the clustered primary key and add a GUID as a separate non-clustered unique column for external references. That gets fast clustered inserts and unguessable public ids, at the cost of one extra column and index.

## Key Takeaways

- `int` identity keys are small and sequential, so they keep the clustered index compact, but they are predictable and unknown before insert.
- Random `Guid.NewGuid()` keys are globally unique and client-generated, but they fragment a clustered index because inserts land at random positions.
- `NEWSEQUENTIALID()` and `Guid.CreateVersion7()` keep GUID uniqueness while inserting in order, which fixes the fragmentation problem.
- HiLo hands out sequential integer ids from the application with no per-row round trip, at the cost of gaps on restart.
- When in doubt, use `int` identity for a single database and version 7 GUIDs for distributed systems.
