# EF Core Compiled Models

Every time an EF Core app starts, it builds an in-memory model of your entities: it scans your `DbContext`, applies conventions, and wires up relationships, keys, and mappings. For a small model that takes milliseconds. For a large model — hundreds of entities — it can take seconds on every cold start. Compiled models move that work to build time.

## How it works

Instead of building the model at runtime, you generate C# code that describes the model and ship it with your app. At startup EF Core loads the pre-built model instead of discovering it by reflection and convention.

## Generating a compiled model

Install the EF Core design package if you have not already, then run the optimize command from your project directory:

```bash
dotnet ef dbcontext optimize --output-dir CompiledModels --namespace MyApp.CompiledModels
```

For a context named `ShopContext` this generates a file like `CompiledModels/ShopContextModel.cs` containing a generated model class:

```csharp
// Generated by 'dotnet ef dbcontext optimize'. Do not edit by hand —
// regenerate it whenever the model changes.
[DbContext(typeof(ShopContext))]
public partial class ShopContextModel : RuntimeModel
{
    private static ShopContextModel _instance;

    public static IModel Instance
    {
        get
        {
            if (_instance is null)
            {
                _instance = new ShopContextModel();
                _instance.Initialize();
                _instance.Customize();
            }
            return _instance;
        }
    }

    partial void Initialize();
    partial void Customize();
}
```

## Using the compiled model

Point your context configuration at the generated model:

```csharp
services.AddDbContext<ShopContext>(options =>
    options.UseSqlServer(connectionString)
           .UseModel(ShopContextModel.Instance));
```

That is the only runtime change. Queries, change tracking, and migrations behave exactly as before.

## The startup-time benefit

Model building is typically the single biggest fixed cost of EF Core startup. With a compiled model, the discovery and convention passes are skipped entirely. The gain scales with model size:

| Model size | Typical cold-start model build | With compiled model |
|-----------|-------------------------------|---------------------|
| ~20 entities | ~50 ms | ~5 ms |
| ~200 entities | ~1–2 s | ~50 ms |
| ~500+ entities | several seconds | ~100 ms |

The numbers above are rough magnitudes, not benchmarks — the point is that the saving grows with the model, and on serverless or container cold starts it is often the difference between a fast first request and a timeout.

## Limits you must know

- **Regenerate after every model change.** Add a property, change a relationship, rename a table — the compiled model is stale until you re-run `dotnet ef dbcontext optimize`. A stale model silently describes the old shape, so make the command part of your build or CI step.
- **Not for dynamic models.** If you build the model at runtime (per-tenant schemas, `OnModelCreating` branches that depend on runtime configuration), a compiled model cannot represent it. Compiled models are for a single, fixed model.
- **Migrations still use the runtime model.** `dotnet ef migrations add` builds the model from your code, not from the compiled output, so your normal migration workflow is unchanged.
- **Some features are unsupported.** Compiled models do not support model-level conventions that run at runtime, lazy-loading proxies configured dynamically, or value converters that need runtime services.

## When to reach for it

Use compiled models when your app has a large model and slow cold starts matter — APIs in containers, Azure Functions, or any app where the first request pays the startup cost. For a small model the saving is negligible and the extra generated file is not worth maintaining.

## Key Takeaways

- `dotnet ef dbcontext optimize` generates a C# model class at build time; `options.UseModel(ShopContextModel.Instance)` loads it at startup.
- The win is startup time: model discovery is skipped, which matters most for large models and cold starts.
- The compiled model must be regenerated after any model change — automate it in CI.
- Compiled models do not fit dynamic, per-tenant, or runtime-built models.
- Migrations are unaffected: they still build the model from your code.
